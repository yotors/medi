# Staff authenticator sign-in

Production requires an authenticator for every staff account. Development may explicitly set `STAFF_MFA_POLICY=synthetic` for unenrolled fictional accounts; this setting is rejected in production. Enrolled accounts always challenge. OTPAuth 9.5.2 uses SHA1, six digits, 30-second periods, 20 random secret bytes, and one adjacent period of clock tolerance. This is not phishing-resistant authentication or security certification.

A password creates a restricted ten-minute session. Enrollment requires a separately delivered, one-use grant. Challenge/recovery/enrollment routes cannot read hospital records. After the hospital lock, every domain authorization rechecks activity, role, factor generation, factor completion, absolute expiry and idle expiry. Sessions last at most eight hours and expire after 30 minutes without workspace activity. Session/status polling does not renew idle time. MFA and password verification have separate bounded attempt budgets. Migration 013 preserves a device session family across cookie rotation. Logout deletes that family under the hospital lock, including a concurrently elevated cookie. Predecessor tokens retain only CSRF-protected logout authority for at most ten minutes, capped by their prior idle and absolute deadlines; they cannot access records or authentication actions. Other device families remain signed in.

## Identity verification and initial enrollment

The hospital owns independent identity verification and private delivery. A fully signed-in administrator opens a named account in Staff administration, enters their own current password, and selects **Issue enrollment grant**. The grant lasts 30 minutes; a replacement revokes previous grants, pending setups and sessions. It cannot reset an existing authenticator. New temporary passwords must be changed before requesting this grant.

For the first administrator, or loss/compromise of every factor, an authorized operator uses a dedicated database credential and the private keyring. The `setup:mfa` examples below are source/development commands: they load the checkout `.env` and must not be mistaken for the packaged release procedure. The command requires explicit hospital code, username, fixed reason, attributable operator reference and a new output file in a private directory:

```
npm run setup:mfa -- grant HOSPITAL USER initial_enrollment OPERATOR_REFERENCE /private/directory/grant.json
npm run setup:mfa -- grant HOSPITAL USER lost_all_factors OPERATOR_REFERENCE /private/directory/reset-grant.json
npm run setup:mfa -- grant HOSPITAL USER compromised_factor OPERATOR_REFERENCE /private/directory/reset-grant.json
```

Do not put credentials in command arguments, stdout, chat or tickets. The command writes mode-0600 output without printing the grant. Deliver it privately only after independent identity verification; remove the delivery file when no longer needed. Operator events identify the operator separately from the target staff member. An existing authenticator cannot be removed using ordinary password reset.

Staff manually add the displayed setup key to their own authenticator, then confirm a current code. Ten 128-bit recovery codes appear once. Keep them privately away from the workstation. Neither browser persistence nor server retry history retains plaintext codes. A lost confirmation response is resolved by signing in using the newly configured authenticator and generating fresh recovery codes under Authenticator security, with password and a fresh factor code.

An unused recovery code invalidates the old factor, ends other sessions, and permits only replacement enrollment. Reloading resumes the same pending setup. If the cookie is lost, sign in with the password and use another unused recovery code or request operator recovery. Remaining old codes survive until replacement confirms; confirmation atomically replaces all codes and rotates cookie/CSRF. Replacing an authenticator from an authenticated session requires current password, unused old-factor proof and new-factor confirmation.

## Keyring and recovery

`STAFF_MFA_KEYRING_FILE` points to private JSON shaped as `{ "current": "version-id", "keys": { "version-id": "64 lowercase hexadecimal characters" } }`. Each key is 32 cryptographically random bytes generated externally. AES-256-GCM uses a new 12-byte nonce and authenticated hospital/account/purpose binding. Keep all referenced old versions when adding a new current version. Startup and readiness decrypt every existing envelope; missing/wrong keys fail closed with generic diagnostics.

Re-encrypt one explicitly identified account at a time after backing up all referenced keys:

```
npm run setup:mfa -- rotate-keys HOSPITAL USER initial_enrollment OPERATOR_REFERENCE /private/directory/rotation-count.json
```

The transaction decrypts, re-encrypts, verifies each new envelope, records the event and writes the verified count privately. Before removing a key version, inspect `envelope->>'keyId'` counts in both `staff_factors` and `staff_mfa_pending`; a referenced version must remain. Readiness will fail if it is removed. Retain every version required by historical backups even after live re-encryption. A failed/uncertain operator transaction must be checked before private output is delivered.

Local release setup adds `.local/mfa-keyring.json` without resetting existing accounts. A short-lived initializer copies it into a dedicated Compose-managed named Docker volume, sets UID1000 ownership and mode0400, and exits. The API and migration/operator containers mount that volume read-only. The initializer alone uses root with file-access/chown capabilities; the application remains non-root with all capabilities dropped. Source mode0600 remains unchanged even when its host UID differs from1000. Existing founder accounts must receive a private grant and configure their own authenticator. The verifier enrolls only its separate `release-*` synthetic fixtures.

New encrypted release archives use manifest format 2 and contain all configured MFA key versions inside the encrypted archive. Backup admission decrypts every envelope in the exported database snapshot using the captured host keyring before publication, so a stale runtime volume or concurrent key rotation cannot silently produce an unrestorable archive. The archive encryption key remains separate. Recovery uses the recorded images and restores their keyring through a private read-only mount. Format 1 archives remain readable and receive their original configuration. Never change `.local/release-backups/pre-mfa-final.medi`, `.local/recovery.key`, or the pinned pre-MFA image reference suffix `6e87f22730907761e0ddd405`.

Production hosting, operator identity governance, independent security review, hospital approval, clinical validation, monitoring and disaster-recovery ownership remain launch decisions. No live deployment or real patient data is authorized by this implementation.

### Review correction safeguards

Prior enrollment remains durable through `factor_generation`, including after the last recovery code is used and replacement is abandoned. Such accounts cannot regain password-only synthetic access; when no proof remains, obtain a fresh independently verified operator grant. Administrator first-enrollment grants are restricted to accounts that have never enrolled.

Keyring files are limited to16KiB,64 key versions and the exact `current`/`keys` object. Runtime/operator admission opens a no-follow nonblocking descriptor, checks a regular private file (0400 or0600 supported), and bounds reads. Parent directories must be real directories owned by the process user or the filesystem root owner and not writable by other users; a root-owned sticky temporary directory is allowed above the private directory. System `/run` parents need no private mode. Provisioning and encrypted archive admission enforce the same object/size bounds. Disabled staff retain encrypted factors and can undergo operator `rotate-keys`; grant issuance still requires an active account.

Startup completes an envelope scan before serving. Readiness shares one scan among concurrent requests and caches either success or failure for two seconds. Scans use one admitted keyring, a repeatable-read cursor with128-row pages and event-loop yields, a one-second connection wait,900ms SQL statement/500ms lock deadlines and a five-second scan budget. A timed-out connection is released if it arrives late; failed scan connections are discarded. Oversized/slow scans fail unavailable rather than skipping records. Request cleanup touches only the current session/account, avoiding locks on another hospital's pending enrollment.

Authenticator maintenance blocks accidental navigation while a write is pending. Loading failure offers explicit retry; setup expiration clears the secret and permits password plus current-factor replacement restart. An uncertain confirmation/code-regeneration reply directs staff to sign in with their authenticator and regenerate codes with fresh proofs. Stop/status use verified release project configuration without requiring or creating MFA files.

The keyring volume survives ordinary stop/start and `docker compose down`; `down -v` deletes it and other Compose volumes, including the database. Restore requires the separate encrypted archive and its key. Do not use volume deletion as a shutdown command.

Review correction budgets: each MFA proof transaction (including limiter reservation/refund) has a 500ms connection-acquisition ceiling, 500ms lock timeout, 900ms statement timeout and 3s total ceiling. Setup status and MFA session lookup use independent 750ms total/200ms statement/100ms lock budgets, and do not consume proof attempts. Status executes only SELECTs with a shared hospital row lock to serialize revocation; PostgreSQL requires an ordinary transaction for that row lock. It performs no expiry deletion. Successful proof mutations clean only their own expired pending/grant rows. Expired retained rows cannot authorize anything. Their encrypted envelopes still participate in readiness and key rotation until cleanup, so referenced key versions must remain available. Expiry denies server authority and clears browser secrets; physical row cleanup waits for scoped account maintenance.

Deadline failures return generic retryable503. A held lock rolls back without consuming a factor. Timed-out connections are destroyed and no subsequent callback SQL can execute. A lost acknowledgement after COMMIT was sent is an uncertain result, so the existing UI explains new-authenticator sign-in and verified recovery-code regeneration; there is no plaintext replay cache. These are per-database-stage ceilings, not a claim that scrypt or the complete HTTP exchange has a single3s deadline.

Rejected authenticated MFA requests accumulate secret-free fixed operation/outcome/hour counters in `mfa_rejection_buckets`. Seven operation enums × three outcome enums ×24 rotating slots permit at most504 rows, with each count capped at1,000,000. No account identifier, guessed actor, IP, password, code, grant or exception text is retained. Interpret only `bucket_hour > floor(extract(epoch FROM clock_timestamp())/3600)-24`; physical stale slots are removed on the next rejection (at most504 dormant rows can remain). Evidence writes have a500ms total/200ms statement/100ms lock budget and happen outside failed proof transactions. If this store fails, the proof remains rejected with its generic error. Successful security events still commit with the proof and cannot fail open. This aggregate is available for the subsequent observability stage; alert delivery is not configured.

Operator output uses a newly and exclusively opened no-follow descriptor, mode0600, in a private directory. All ancestors must be symlink-free and owned by root/current UID without group/other write permission; root-owned sticky temporary parents are permitted, consistent with keyring admission. The operator records file ownership before the first write, removes its own partial file on write/commit failure, and never removes a preexisting output. After any prior enrollment, including abandoned final-code recovery, use a recovery reason rather than `initial_enrollment`.

Setup status also admits at most30 requests per authenticated account per60-second window per API process, shared across that account's sessions. Its in-memory admission map holds at most4096 accounts, removes expired entries on admission and fails closed with429 at capacity. No proof-attempt budget is consumed, no database mutation occurs, and process restart resets this read-only flood budget. Multiple API replicas each enforce their own bound; a distributed ingress limit remains an infrastructure decision.


### Packaged local release operator procedure

Use the running, verified `medi-release-local` project and its private `.local/release.env` and mounted keyring. From the product checkout, create a private output directory (`mkdir -m 700 .local/operator-delivery`), then run one explicitly named operation:

```
npm run release:mfa -- medi-release-local grant HOSPITAL USER initial_enrollment OPERATOR_REFERENCE .local/operator-delivery/first-grant.json
npm run release:mfa -- medi-release-local grant HOSPITAL USER lost_all_factors OPERATOR_REFERENCE .local/operator-delivery/recovery-grant.json
npm run release:mfa -- medi-release-local rotate-keys HOSPITAL USER compromised_factor OPERATOR_REFERENCE .local/operator-delivery/rotation-count.json
```

Replace the uppercase placeholders with the independently verified hospital code, named account and attributable operator reference. `compromised_factor` is also available for a reset grant. The wrapper rejects other project names, unexpected running API image/source context, unsafe output ancestry and preexisting output. It runs the exact current API image as UID1000 on the existing release data network, using the migration/owner credential and the read-only keyring volume. The packaged CLI verifies `product_studio_release` and `medi_migrator` before any mutation. No release credential is copied into `.env`, passed in a process argument, printed by Compose configuration rendering, or written to stdout. Private result retrieval uses a short-lived nonroot helper with a private directory in its disposable writable layer and a new mode0600 host output. The API stays read-only. Docker copies the result without routing secret bytes through stdout; forced helper removal deletes that temporary layer. Cleanup failure reports a fixed check ID and helper name, returns failure and requires removal before delivery. All Docker subprocesses are bounded to20seconds; the keeper exits after60seconds and cleanup removes the container.

Open the result only in a private operator context; do not paste it into terminals with captured output, tickets or chat. Verify its hospital/account before independent delivery. Remove the file after delivery. A command failure can be uncertain after COMMIT: check account state and issue a replacement grant if necessary, rather than assuming rollback. The CLI uses the proof transaction's500ms acquisition/lock,900ms statement and3s monotonic total budget, after the separately bounded readiness scan. Small synchronous exclusive descriptor writes cannot complete after timeout cleanup; the wrapper's subprocess bound also covers filesystem stalls. Existing output is never deleted.

MFA attempt reservations charge concurrent work before proof verification. Each account gets10 failed/abandoned proofs and each IP50 in a15-minute window. Committed successful proofs refund only their own still-current window, so correct shared-workstation onboarding does not consume the failure budget. A refund failure leaves a conservative charge but does not turn committed success into an error. Login, password reauthentication and status budgets remain separate.

Interrupted enrollment start, recovery, or authenticator replacement reconciles this account and device session family before resuming its pending setup. Failed reconciliation offers **Resume authenticator setup** and clears submitted passwords/codes/grants. It never requires resubmission of a consumed final recovery code. Authentication-read rejection sends no cookie mutation, so an old delayed401 cannot erase a newly elevated cookie. Administrator grants carry the committed database expiry and are cleared at that deadline or visibility validation with replacement guidance.
